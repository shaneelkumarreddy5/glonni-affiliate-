# APITxT customer phone OTP integration

Status: sender deployed; the HTTPS Send SMS hook is saved but disabled. The customer request/verification UI is implemented and gated off unless the server-only `PHONE_OTP_ENABLED=true` flag is set. Email/admin auth and the customer phone OTP request use Glonni's existing signed arithmetic challenge. Supabase-native CAPTCHA is intentionally deferred. The owner confirmed the endpoint and matching hook secret. No real SMS has been sent.

## Verified provider contract

Source: [APITxT OTP API](https://apitxt.com/developer/otp-api), read on 12 October 2026.

- POST `https://apitxt.com/api/sendOTP`, `application/x-www-form-urlencoded`.
- Send `authkey`, `mobile` (91 + Indian mobile number), `otp` supplied by Supabase, `channel=sms`, `country=91`, and `template_id` when using a custom template.
- Accept only HTTP success with JSON `status: "success"`. This indicates provider acceptance, not confirmed delivery.
- SMS credits are charged per request. Do not auto-retry failed or timed-out requests.

APITxT documents a system-default SMS configuration when `template_id` is omitted. The adapter supports it; confirm its message/sender with the owner before a live test. If using a custom Glonni template, it should be approved and contain `{otp}`. `template_id` is APITxT's internal SMS template ID, not a DLT template number.

## Credentials: save only in Supabase Edge Functions → Secrets

| Name | Value |
| --- | --- |
| `APITXT_AUTH_KEY` | The APITxT API authentication key; never put it in browser code, chat, screenshots or Git. |
| `APITXT_SMS_TEMPLATE_ID` | Optional: the internal ID of the approved Glonni SMS OTP template; omit to use APITxT's documented default. |
| `SEND_SMS_HOOK_SECRET` | Signing secret generated by Supabase's Send SMS HTTP Hook, including `v1,whsec_`. |
| `APITXT_SMS_ENABLED` | Leave absent/false until setup and spending controls are ready; true enables billable sends. |

Deploy `apitxt-send-sms` with JWT verification off only because the function verifies the Supabase Auth signature, signed timestamp and payload with pinned `standardwebhooks@1.0.0`. It does not accept the ordinary publishable key as authentication and does not need a service-role key. It supports configured rotation secrets separated by `|`.

## Remaining activation sequence

1. Confirm `APITXT_AUTH_KEY` and `SEND_SMS_HOOK_SECRET` exist in Supabase Edge Function secrets without revealing their values; confirm whether to use APITxT's default SMS configuration or an approved custom template. Save `APITXT_SMS_TEMPLATE_ID` only for a custom template.
2. Keep the signed arithmetic challenge on the customer email sign-in/sign-up/password-reset, admin sign-in, and phone OTP request forms. It is checked server-side and expires after five minutes. It is a lightweight early-stage speed bump, not a substitute for Supabase Auth's own limits and not a barrier to direct calls to Supabase Auth. Supabase-native CAPTCHA is intentionally left disabled until traffic justifies it.
3. Supabase's OTP/magic-link verification limit is set to 10 requests per 5 minutes per IP (saved). The project-wide SMS sending cap remains 30 per hour; Supabase currently marks that field non-editable on this Free project. The normal sign-in/sign-up limit remains at its current 30 requests per 5 minutes per IP. Keep these controls in place and do not increase them without a reviewed traffic/spend need.
4. Phone login remains gated by the server-only feature flag. When a controlled live test is approved, enable phone authentication with phone confirmation required (automatic confirmation OFF) and six-digit codes with a short expiry. Do not change admin TOTP MFA.
5. The customer request/verify UI uses the app's server route to validate the arithmetic challenge, then calls Supabase `signInWithOtp`; `verifyOtp({ phone, token, type: 'sms' })` verifies with Supabase and establishes the session. Never generate a login session based on APITxT's delivery response. Keep keys and OTPs out of logs/URLs.
6. Ask the owner to approve one SMS to their own test phone. Only after approval, enable the Send SMS hook, `APITXT_SMS_ENABLED`, and `PHONE_OTP_ENABLED` for the controlled test; test correct/wrong/expired codes and resend limits, confirm a customer profile is created with no admin permissions, and test existing email login and admin MFA. After testing, keep enabled only if live use is intentionally approved.

Do not silently merge a new phone account with an existing email account. Adding/changing a verified phone on an existing account requires a separately reviewed flow. This sender currently rejects `phone_change` and non-India/non-six-digit requests.

Rollback: disable the website's mobile-login entry, disable phone signup/the SMS hook and set `APITXT_SMS_ENABLED=false`. Keep existing customer records, email login and admin MFA intact. No database migrations or deletions are required by the sender.
